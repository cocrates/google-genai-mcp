# Speech Chunk Failure Recovery

## Concern
장문 Speech를 여러 청크로 나눠 생성하는 중 일부 청크가 실패하면 어떻게 처리할 것인가?

## Status
approved

## Context
- `adr/speech-long-form-chunking.md` (approved, Option C): 임계값 초과 시 문단/문장 단위로 나눠 순차 생성 후 병합 저장. 청크 수 N이 커질수록 **어느 하나는 실패한다**고 가정해야 한다.
- 실패 유형이 성질상 다르다:
  - **일시적/재시도 가치 있음** — 429 rate limit, 5xx service. Google 문서는 TTS가 드물게 오디오 대신 텍스트 토큰을 반환해 **500으로 실패**하므로 자동 재시도 로직을 구현하라고 명시한다.
  - **영구적/재시도 무의미** — 400 `PROHIBITED_CONTENT`(프롬프트 분류기 오탐), 잘못된 입력. 실제로 본 저장소 실험에서 대본 일부 슬라이스가 sensitive-words 400으로 차단된 사례가 있다. 같은 텍스트를 다시 보내도 계속 실패한다.
  - **치명적** — 인증 실패, quota 초과. 이후 청크도 전부 실패한다.
- 기존 `withRetry`(`src/core/errors.ts`)는 rate limit 3회, service 2회, quota/auth 0회로 이미 분류·백오프를 제공한다. 청크 루프는 이를 재사용할 수 있다.
- 비용/시간 관점: 12분 분량이 수십 청크로 쪼개진 상황에서 **마지막 청크 하나 때문에 전체를 재생성**하면 앞선 성공분의 API 비용과 대기 시간이 버려진다.
- CLI는 동기 기본이고 Ctrl-C 중단이 가능하다(ASR-011/ASR-017). 사용자는 중간에 끊을 수 있으므로 중단 지점 복구와 동일한 문제를 공유한다.

## Decision
**Option C — 청크별 재시도 + 부분 캐시 & Resume**
청크마다 기존 `withRetry` 분류(rate limit 3회 / service 2회 / quota·auth 0회)를 적용하고, 성공한 청크 오디오는 캐시에 보존한다. 실패 시 부분 산출물은 저장하지 않고 중단하되, 동일 요청 재실행 시 캐시된 청크는 건너뛰고 실패 지점부터 이어서 생성한다. 실패를 무음으로 덮는 best-effort 동작은 채택하지 않는다.

## Options

### Option A — Fail fast (첫 실패 시 전체 중단, 저장 없음)
- 청크 하나라도 실패하면 즉시 에러로 종료하고 부분 결과를 버린다.
- Pro: 구현이 가장 단순. 불완전한 오디오가 만들어질 위험 0. 현재 단일 요청 동작과 의미가 같다.
- Con: 마지막 청크 실패 시 앞선 모든 성공분(비용·시간)이 버려진다. 400 오탐 한 건이 12분 대본 전체를 막는다.

### Option B — 청크별 재시도 후 Fail fast (재시도 O, 부분 저장 X)
- `withRetry` 분류를 청크 단위로 적용(rate limit/5xx 백오프 재시도). 재시도 소진 또는 영구 오류면 A처럼 전체 중단.
- Pro: Google이 경고한 무작위 500을 대부분 흡수. 구현 부담 작음(기존 유틸 재사용). 결과는 항상 "완전한 오디오 또는 실패"로 명확.
- Con: 영구 오류(400 차단)에는 여전히 무력. 부분 결과 폐기 문제 유지.

### Option C — 청크별 재시도 + 부분 캐시 & Resume
- 청크 오디오를 작업 디렉터리(예: `{dataDir}/chunks/{hash}/{NNN}.pcm`)에 저장. 실패 시 중단하되 성공분은 캐시에 남긴다. 같은 요청 재실행 시 캐시된 청크는 건너뛰고 실패 지점부터 이어서 생성.
- Pro: 재실행 비용이 실패분에 한정. Ctrl-C 중단 복구와 같은 메커니즘으로 해결. 400 오탐도 사용자가 해당 문장만 고쳐 재실행하면 나머지는 재사용.
- Con: 캐시 키 설계(텍스트·voice·model·경계 규칙 해시), 캐시 무효화·정리(GC) 필요. 청크 경계가 바뀌면 캐시 대부분 무효. 구현·상태 관리 복잡도 최상.

### Option D — Best-effort: 실패 청크를 무음/스킵으로 대체하고 계속
- 실패 청크는 동등 길이 무음(또는 생략)으로 채우고 끝까지 진행, 완료 후 실패 목록을 경고로 보고.
- Pro: 항상 산출물이 나온다. 긴 나레이션에서 한 문장 누락은 수동 보정이 쉬울 수 있다.
- Con: **조용히 내용이 빠진 오디오**가 성공처럼 보일 위험. "검토하지 않은 산출물" 리스크. 무음 길이 추정도 부정확.

## Tradeoffs

| | A. Fail fast | B. 재시도+Fail fast | C. 재시도+Resume | D. Best-effort |
|---|---|---|---|---|
| 일시적 5xx/429 내구성 | 없음 | 좋음 | 좋음 | 좋음(무시) |
| 영구 400 대응 | 전체 실패 | 전체 실패 | 실패분만 수정·재실행 | 내용 누락 |
| 재실행 비용 | 전체 재생성 | 전체 재생성 | 실패분만 | 해당 없음 |
| 산출물 신뢰성 | 높음 | 높음 | 높음 | **낮음(누락 은폐)** |
| 구현 복잡도 | 낮 | 낮~중 | 높 | 중 |
| 상태/캐시 관리 | 불필요 | 불필요 | 필요(GC 포함) | 불필요 |
| Ctrl-C 복구 | 불가 | 불가 | 가능(부수 효과) | 불가 |

## Recommendation (optional)
- **B를 즉시 채택하고, C를 후속 단계로 두는 2단계 접근**을 추천한다.
  - 1단계(B): 청크 루프에 기존 `withRetry` 적용 + 실패 시 **몇 번째 청크, 어떤 문장, 어떤 분류의 오류**인지 명확히 보고. 이것만으로 Google이 경고한 무작위 500은 대부분 사라진다.
  - 2단계(C): 캐시·resume은 실제로 장문 재실행이 아플 때 도입. 캐시 키·GC 결정이 필요하므로 별도 ADR/작업으로 분리.
- **D는 기본값으로 비추천.** 내용 누락이 성공으로 보이는 것은 이 프로젝트의 검토 원칙과 정면 충돌한다. 굳이 원하면 명시적 opt-in 플래그(예: `--allow-partial`)로만 열어야 한다.
- 영구 오류(400 `PROHIBITED_CONTENT`)는 재시도 대상에서 제외하고, **문제 문장을 그대로 사용자에게 보여주는 것**이 실질적인 해결책이다. 사용자가 그 문장만 고치면 되기 때문이다.
- 인증/quota 오류는 남은 청크를 시도하지 않고 즉시 중단한다(무의미한 N배 실패 방지).

## Consequences
- 청크 진행 상황(`3/27`)과 실패 청크의 인덱스·원문 발췌·오류 분류를 로그·CLI에 노출해야 한다.
- 부분 산출물(`.wav`)은 저장하지 않는다. 캐시는 내부 작업 파일이며 사용자 산출물이 아니다.
- 캐시 위치·키 구성·보존/정리 정책, resume 표면(자동 vs 플래그)이 필수 구현 항목이 된다.
- 영구 오류(400 `PROHIBITED_CONTENT`)는 재시도하지 않고 문제 문장을 그대로 제시한다. 사용자가 해당 문장만 수정해 재실행하면 나머지 청크는 캐시에서 재사용된다.
- 인증/quota 오류는 남은 청크를 시도하지 않고 즉시 중단한다.
- **하지 않을 것:** 실패를 무음으로 덮어 성공처럼 보고하는 동작(Option D). 필요 시 명시적 opt-in 플래그로만 검토한다.
